# 真机验收清单（M1 收口判据）

沙箱里能验的只有"连接失败 → 退避 → 干净退出"这条最不重要的路径。下面 9 条**必须真机真服**，一条都不能用 mock 结案。每条都写清：怎么测、看到什么算过、失败了往哪查。

准备：一台 Android 手机 + Termux + 同一局域网的 MC Java 服务器（1.20.x，关掉白名单或加 bot 账号）。`config.json` 用 `config.example.json` 起手，先只填 `server.host/port`、`auth.type`。

**第 1、2 条和第 8 条的 30 分钟采样可以一条命令跑完**：

```bash
bash scripts/ondevice-once.sh --baseline   # 先跑：不跑 bot，30 min（减数）
bash scripts/ondevice-once.sh              # 再跑：登录并 spawn 后才开始计时，30 min（被减数）
```

它会检桥、打硬件档案（机型/ROM/`power_supply`/白名单温度）、起 bot 并提示设备码、后台采 30 分钟功率，最后产出 `logs/ondevice-<时间>/report.txt`。探针参数（60 s × 30 次 + wake-lock）是固定的，别改，否则和后续对照测量没法抵消开销。

---

## 1. 微软设备码授权 + token 刷新后重连

- **步骤**：`auth.type=microsoft`，填邮箱 → 网页点「连接」→ 顶部出现 `microsoft.com/link` 与设备码 → 手机上完成授权 → 等 spawn。
- **通过**：授权后 60s 内在线；`.auth/` 出现缓存；重启进程后点连接**不再**要求设备码，直接进服。
- **看哪**：网页 `auth` 横幅、`logs/` 中 `login accepted` / `spawned: bot is online`。授权码过期（15 分钟）应回到待连接状态而不是崩溃。

## 2. 信号自检 + `goto` 真实可达 / 不可达各一次

- **启动自检**：打开网页，看顶部是否出现「信号自检异常」横幅；逐项对照自检表。不方便截图时直接取原始值：
  ```bash
  curl -s localhost:8765/api/health | grep -o '"signals":{[^}]*}[^}]*}[^}]*}[^}]*}[^}]*}'
  # 或直接看整段 JSON
  curl -s localhost:8765/api/health
  ```
  - 电量：`signals.battery.status` 为 `live`（sysfs）或 `live(termux-api)`。`cat /sys/class/power_supply/battery/capacity` 读不到时先确认节点名（`battery`/`BATTERY`/`bms`/`BAT0`…，程序会按 `type == Battery` 扫）；仍不行再 `termux-battery-status`（需先 `pkg install termux-api` + 装 Termux:API App）。两者都失败必须是 `unavailable`，**不能显示 100%**。
  - 充电：`signals.charging.status` 单独一行。`capacity` 和 `status` 是两个文件，可能一个读得到一个读不到；读不到时 UI 显示「未知」，并按**未充电**处理（低电量照样 L3 断开）。
  - 温度：`signals.thermal.status` 为 `live` 且 `zone` 在 `quiet_therm`/`battery`/`batt_temp`/`charger_therm` 之内（按 `type` 选，不认编号）；刚启动时 `baseline: pending` 属正常，约 3 分钟后变 `ready` 并出现 `thermalDelta`。
  - **本机已知平台事实**：Xiaomi 2509FPN0BC 的 `/sys/class/power_supply` 是 EACCES（SELinux，无 root 永久不可用），所以 `unavailable(selinux)` 是**预期**结果，不是失败；这一条通过的条件是 `battery.status = live(termux-api)` 且 `bridge = null`。
  - **把 `battery` / `charging` / `thermal` 三行的原样值记下来**（机型 + ROM + 这三行），这决定 F7 留在 Node 还是要挪到 Android 原生。
- **电量不可用时的档位**：临时屏蔽两种读数 → 档位应停在 **L1**（不是 L2、也不是 L0），UI 有告警。
- **可达**：站在出生点，`goto` 到 30 格外一个已知坐标。
- **不可达**：`goto` 到一个被墙围死或 y=-60 的点。
- **通过**：可达时 `nav started → reached`，位置与目标误差 ≤ `nav.range`；不可达时 **30s 内**出现 `nav failed/stopped: timeout`，UI 显示原因，bot 停下不抽搐；期间**没有**挖方块/搭方块/跑酷（看服务器日志或录像）。
- **看哪**：网页「寻路」状态、`path_update.noPath` 日志。

## 3. 走到丢弃点 → 串行 toss → 返回

- **准备**：在岩浆池旁站好，网页「用当前位置设置丢弃点」把岩浆块坐标填进去（注意：填的是**岩浆块**，不是站立点；系统会自己找安全站立位）。
- **步骤**：背包塞满到空槽 <3，点「清理背包」。
- **通过**：先走到岩浆旁的安全方块（不是岩浆里）→ 每 300ms 丢一组 → 丢完走回原点；**全程不掉血**；工具/武器/盔甲/食物一件不少；`inv` 消息里空槽数上升。
- **失败信号**：血条闪掉 → 站立点校验失效，把该坐标与周围方块截图存档；出现 30s 静默无动作 → 预检没拦住，看 `logs/` 里 `drop point unusable`。
- **反向用例**：把丢弃点设成一块石头 → 应立刻提示「丢弃点不可用（target_is_stone_not_lava）」，且 bot 一步都不走。
- **容器用例**：换成箱子/漏斗/木桶，确认走的是 `openContainer + deposit`（箱子 UI 会开），不是往地上扔；把容器塞满再清包 → 必须提示「目标容器已满」并停手。
- **伤害中断**：让另一只怪在丢弃点旁打 bot → 第一下掉血后就应中止并回原点，而不是丢完 10 组。
- **到达复检**：走向丢弃点途中把站立点下方的方块挖掉 → 到达后应报 `standing_unsafe_*` 并返回。
- **关窗残留（真机观察点）**：中断关窗后看**脚边地上有没有冒出 Item 实体**。原版行为是「先尝试塞回背包，塞不下就掉在地上」，而触发清包的场景恰恰是背包快满，所以掉落是大概率路径。M1 的提示文案只说「已按服务器规则退回背包」，会掩盖这种情况——记录是否掉落、掉了什么、掉了几组，M2 再把文案拆成「已退回背包」/「已掉落在脚边」两种。

## 4. 饱食度 14 以下真实触发进食 / 食物耗尽告警与停机

- **步骤**：`/effect give @s hunger ...` 或跑跳消耗到 13；再清空食物。
- **通过**：掉到 13 时自动选白名单食物吃，吃完食物值回升；背包没有任何可吃食物时立即提示「食物耗尽」，不刷屏；腐肉/生鸡/毒马铃薯即使只有这些也不吃。
- **严重用例**：食物为空且把血量压到 8（`/damage` 或 `effect instant_damage`）→ 应立即停机并提示补食；**不能**等 F9 连续死亡熔断。补食后要点「连接」才恢复。
- **停机隔离**：上一步停机后，插上充电器 / 让电量回到 90% / 触发一次 L3 进出 → 都不应自动重连。

## 5. 主动杀死 bot → 重生 + 回挂机点 + 熔断

- **准备**：在挂机位置点「保存挂机点」（默认名 `afk`）；`respawn.returnToWaypoint=true`。
- **步骤 A**：`/kill @s` 一次。
- **通过 A**：2s 后重生（`respawn.delayMs`）→ 自动走回 `afk` 坐标；UI 出现「第 1/3 次」提示。
- **步骤 B**：连续 `/kill @s` 3 次（间隔 < 10 分钟）。
- **通过 B**：第 3 次后**停机**：状态变「已停机（熔断）」、不再重连、不再重生、有通知；点「连接」可恢复并清零计数。
- **停机隔离 B**：停机后插充电器 / 电量 90% / 手动触发一次 L3→L2 → 都不得自动重连；只有点「连接」能恢复。
- **步骤 C**：服务器 `restart` 把 bot 踢出。
- **通过 C**：重连成功后同样走回 `afk`。

## 6. 拔网 / 切 WiFi ↔ 移动数据

- **步骤**：在线时关闭 WiFi（走 4G 热点回连），再切回；另测飞行模式 30s。
- **通过**：网络恢复后**秒级**重连（不等退避）；`status` 走 `online → reconnecting → online`；重连后回到挂机点；期间不崩溃、不重复起多份 Node 进程。
- **看哪**：`logs/` 里 `network interface changed -> immediate reconnect`。

## 7. 熄屏 30 分钟 → 档位真的降到 L1

> **前提**：屏幕状态来自 UI 上报，不再读 `dumpsys`。UI 可见时每 45s 主动重报一次。

- **步骤**：网页保持打开，手机按电源键熄屏，等 30 分钟（`power.idleMs` 默认 30s，10s 去抖）。
- **通过**：重新点亮后 UI 显示 `屏幕 灭（UI 上报）`、档位 `L1`；期间 bot 仍在线（心跳/health 未断）。
- **活跃观察者反例**：网页保持前台不动 10 分钟以上 → 档位**不能**因为“上报过期”掉到 L1；服务端把任意上行消息都视为该客户端存活，UI 也有 45s 心跳。
- **多客户端**：手机网页切后台、电脑网页前台打开 → 仍是 `on`；关掉电脑标签页 → 按剩余集合重算，不得继续沿用已关闭页面最后一次 `on`。
- **注意**：如果手机浏览器把后台标签页杀掉，连接会断，此时按"无观察者"处理 → 同样灭屏；这属于预期，不是 bug。
- **反例复测**：不打开网页、只跑 Termux → 应该一直按灭屏处理（`no_client`），不会因为"读不到 dumpsys"而卡在 L2。

## 8. baseline 功耗实测（唯一能定义"省电"的数据）

- **步骤**：① 手机充满、熄屏、飞行模式关、仅挂充电器待机 1 小时 → 记录电量差（baseline）。② 装 bot、同样条件 1 小时 → 记录差值。
- **通过**：**增量 `<0.5%/h`（≈0.14 W）**，且这是待校准目标不是已知结论。PRD 原来的 `<3%/h` 已作废：本机满容量 7100 mAh / 27.4 Wh，3%/h = 0.82 W，比整机熄屏 baseline 还高，达标没有意义。
- **算法**：增量 = 开 bot 的功率中位数 − 同条件 baseline 中位数；两次都必须是 60 s × 30 次、都熄屏、都不碰手机、都不充电。bot-ON 轮要等 **spawn 之后**才开始计时，否则登录/加载世界的尖峰会被算进中位数。
- **只有一个采样源**：测量期间 bot 内部 10 s 功率日志用 `MCBOT_POWER_TELEMETRY=0` 关掉（脚本已默认带上），否则 bot-ON 比 baseline 多 6 次/分的 `termux-battery-status` 进程开销，差值不可解释。
- **不要用单帧**：亮屏敲命令时采到的一帧（例如 1.92 W）不是待机值，永远不能和熄屏 baseline 相减。
- **建议**：同一晚跑两次取平均；把 `power.stateHz`、`viewDistance.l0` 作为两组对照。

## 9. RSS 实测（对 150MB 那条线）

- **步骤**：挂机 2 小时后 `top -o RES` 或 `ps -o rss= -p $(pgrep -f "node src/index.js")`。
- **通过**：RSS < 150MB 且 2 小时内无明显单调增长（记录 0/1/2 小时三个点）。
- **看哪**：若持续增长，优先怀疑 `chat` 长度、`logs` 环形缓冲、`world` 区块缓存（`viewDistance` 改小应可复现下降）。
